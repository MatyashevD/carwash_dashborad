# Спецификация: промо-план и RFM по данным Лейки

Универсальное описание методики для **людей и моделей**. Не привязано к номеру агента, числу моек или городу: партнёр может быть с **одной точкой** или с **сетью** — конкретная топология и фильтры задаются в **реализации** (скрипт сборки отчёта).

---

## 1. Назначение

- Собрать **промо-план** для владельца: RFM, списки под рассылку, бюджет по инициативам, при необходимости погода и когорты.
- Внешний вид и листы выравниваются по сетевому шаблону (например `H2O_Saransk_Promo_Plan.xlsx`, `AquaBot_Samara_PREDECTIVE.xlsx`): маркетинговые сегменты, русские названия инициатив в бюджете.

**Артефакты** (имена файлов в реализации произвольны):

| Тип | Содержание |
|-----|------------|
| Рабочая книга `.xlsx` | Пакет для владельца |
| Краткий `.md` | Выжимка по периоду (опционально, генерируется сборщиком) |

---

## 2. Один объект и сеть моек

- У партнёра в Лейке может быть **одна** автомойка или **много** объектов.
- **RFM (квантили R, F, M)** всегда считаются на **явно заданной выборке**: например все клиенты Лейки по партнёру в периоде, или **отдельно по каждому адресу** — это **решение конкретного отчёта** и должно быть задокументировано в коде сборщика.
- Лист **«Обзор и модель»** в шаблоне обычно содержит карту объектов и сводку по месяцам; при сети — несколько строк объектов и блок «итого по сети».
- **Погода и загрузка:** координаты и таймзона берутся из **географии объекта(ов)** в реализации (один город или несколько — по правилам продукта).

---

## 3. Входные данные и фильтры (типовые)

- **Источник:** CSV выгрузки Лейки (`orderTable`), период и имена файлов задаёт **сборщик**.
- **Партнёр:** отбор по полю партнёра (например совпадение с `Agent #…` или идентификатором — **как принято в вашем пайплайне**).
- **Тип оплаты:** как правило только оплаты, относящиеся к мойке (например **`Мойка автомобиля`**).
- **Канал:** для клиентской базы под промо часто берут только **Лейку**; платежи через агрегаторы (Яндекс, банк-эквайринг и т.д.) могут исключаться как не относящиеся к «клиентам приложения».

Конец анализа — по **максимальной дате оплаты** в применённых фильтрах (или по фиксированному дню — если так задано в реализации).

---

## 4. Визиты и метрики клиента

- Транзакции объединяют в **визиты**: если между соседними оплатами одного телефона разрыв **больше порога в минутах** (в эталонной реализации 30 мин), начинается новый визит.
- На клиента: **LTV** (сумма по визитам), **число визитов**, **последний визит**, **recency** — дней до конца анализа.

---

## 5. R, F, M (квантили 1–5)

На выбранной совокупности клиентов:

| Метрика | Смысл | Примечание |
|---------|--------|------------|
| **R** | Свежесть | Меньше дней с последнего визита → **выше** балл (ранг recency инвертируется) |
| **F** | Частота | Больше визитов → выше балл |
| **M** | Деньги | Выше LTV → выше балл |

**Квантиль:** ранг по выборке, нормировка в 5 групп по численности (`ceil` от доли), баллы 1…5 — **не** фиксированные пороги в днях/рублях.

Внутренний код **R-F-M** может храниться в данных; **в Excel для владельца** в первую очередь показываются **маркетинговые имена** сегментов (см. §6).

---

## 6. Маркетинговые сегменты (7 имён)

Один сегмент на клиент — правила в виде цепочки условий (**R = 5** в квантиле = самая свежая аудитория). Порядок проверки **сверху вниз**; первое совпадение задаёт сегмент:

| Имя | Условие (кратко) |
|-----|------------------|
| Champions | `R≥4`, `F≥4`, `M≥4` |
| Loyal | `R≥4`, `F≥4` (после Champions) **или** оставшиеся с `R≥4` после Promising |
| Promising | `R≥4`, `F≤2` |
| Need Attention | `R==3`, `F≥3`, `M≥3` |
| At Risk | `R==2`, `F≥3`, `M≥3` |
| About to Sleep | `R==2` (прочие), либо `R==3` не попавшие в Need Attention |
| Hibernating | `R==1` или остаток |

**Порядок строк** в сводках и бюджете фиксирован:  
`Champions → Loyal → Promising → Need Attention → At Risk → About to Sleep → Hibernating`.

**Русские инициативы** в бюджете (пример): Удержание лучших, Рост частоты, Конверсия новых, Лёгкая реактивация, Срочная реактивация, Реактивация уходящих, Возврат потерянных — задаются словарём в коде (`INITIATIVE_RU` или аналог).

---

## 7. Две механики стимула и бюджет по сегменту

### 7.1. Бонусы на бонусный счёт (50 / 30 / 50 ₽)

Для сегментов **Champions, Loyal, Promising** суммы **50 / 30 / 50 ₽** в отчёте — это **начисления на бонусный счёт** в приложении Лейки, **не** скидка «ввести промокод и получить % off». В таблице Excel колонка может называться «Промокод» по шаблону файла, но по смыслу это **идентификатор кампании / учётной акции** для начисления бонусов.

В **push** для этих сегментов формулировки в духе: начислен VIP-бонус или бонус N₽ **на бонусный счёт**, благодарность за лояльность и выбор мойки — **без** текста вида «промокод VIP50…» для самой суммы бонуса.

### 7.2. Промокод на оплату мойки (100%)

Для сегментов **Need Attention, At Risk, About to Sleep, Hibernating** — механика **«100% оплата промокодом»**: клиент **активирует код** в приложении для бесплатной/лимитной мойки по правилам акции. Тексты push описывают **активацию промокода**, а не начисление бонусов рублей на счёт.

### 7.3. Общее

- На каждый сегмент задаётся: **механика**, **формулировка суммы/условия**, **строка приоритета** (часто 1–7). **Код в колонке «Промокод»** — конфиг партнёра (суффиксы города/агента); для бонусных сегментов трактовать как **код кампании начисления**, для реактивации — как **код активации в приложении**.
- Бюджет по строке сегмента можно вязать к **репрезентативному R** (например медиана R в сегменте); для пустого сегмента — заглушка из типичных значений по сегменту.

**Пример оценки бюджета** `budget_estimate_for_r(r, n)` (не юридический офер, ориентир для таблицы):

| Условие по R | Бюджет | Периодичность |
|--------------|--------|----------------|
| `R ≥ 4` | `n × 50` ₽ | Ежемесячно |
| `R == 3` | `n × 35` ₽ | Ежемесячно |
| `R == 2` | `n × 100` ₽ | Однократно |
| `R ≤ 1` | `n × 200` ₽ | Однократно |

Строка **ИТОГО** — сумма по инициативам; блок «по объектам» при сети может дублировать итоги по точкам.

---

## 8. Push: пачки без имени и разные формулировки по механике

- Рассылка **пачками** по спискам (сегмент / выгрузка), **без** подстановки имени в текст push.
- **Бонусы на счёт (Champions / Loyal / Promising):** единый шаблон на сегмент — благодарность за выбор мойки, **начисление VIP-бонуса или бонуса N₽ на бонусный счёт**, благодарность за лояльность (в духе уже использовавшихся пушей: *«Вам начислен VIP-бонус 50₽ на счёт. Спасибо за вашу лояльность.»*). **Не** писать в тексте, что 50₽ — это «промокод» в смысле купона на скидку.
- **Промокод на мойку:** активация кода в приложении, условие бесплатной/лимитной мойки; формулировка отдельная от бонусных пушей.
- Колонка **«Имя клиента»** в таблице для справки, **не** подставляется в push.

## 9. Структура Excel (типовые листы)

| Лист | Назначение |
|------|------------|
| **Обзор и модель** | Объекты, сводка по месяцам, итог по сети, кратко про модель |
| **RFM сегменты** | Сводка по 7 сегментам; при сети — дополнительные блоки по объектам |
| **Клиенты для промо** | Строка на клиента, промокод, текст push |
| **Погода и загрузка** | Если используется — погода по координатам + дневная загрузка |
| **Когорты retention** | Пересечения периодов, ядро |
| **Бюджет промо** | Инициативы, ИТОГО, пояснение механик |

Оформление (ширины, цвета шапок) может подтягиваться с эталонной книги, если она есть рядом со скриптом.

## 11. Реализация в репозитории

Конкретный скрипт (имена CSV, фильтр партнёра, суффиксы промокодов, один объект vs несколько) — **пример внедрения**, а не часть универсальной спецификации. Методика расчёта должна **согласовываться** с разделами §3–§8 выше.

При изменении правил обновляйте **и код, и этот файл**, чтобы модели и аналитики опирались на одно описание.

---

## 12. Синхронизация с кодом

При смене сегментации, промокодов или формул бюджета вносите правки **в реализацию и в `PROMO_PLAN_SPEC.md`** одновременно.
